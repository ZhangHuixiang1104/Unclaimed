# 当前数据与状态契约

以现有代码为准：`frontend/src/types/archive.ts`、`frontend/src/data/objects.ts`、`frontend/src/stores/archive.ts`、`frontend/src/stores/account.ts`、`backend/app.py`。本文件不再定义另一个尚未实现的 `app/src/domain/model.ts`。

## 稳定标识与事件

物件 ID 固定为 `list / map / battery / shoes / bowl`，按此顺序解锁。每件当前有三处 `Clue`、三个故事内 `Conclusion`、两个本件专属 `ScreeningDecoy`。线索 ID 与存档相连，改变它们必须更新 `contentVersion` 并处理旧档。

单件状态：`locked → available → investigating → archived`。只在前一件 `archived` 后开放下一件。调查操作依次是发现线索、筛掉两项无据说法、给三项判断盖“可确认／可推测／仍未知”印章、核验、单独揭露史实、阅读、建档。归档后只读。五件各自调查，不再以饭碗回执补完名单的任务。

`confirmed/inferred/unknown` 表示**故事内证据级别**，不代表某个真实历史人物或文物已被鉴定。历史背景由 `historyRecords.ts` 独立提供，并标识外部来源或待核接入位。真实手迹与游戏名单不可共用同一物件身份。

## 云存档与升级

后端 `Progress` 与前端 `SavedProgress` 包含 `contentVersion`、档案员编号、五件记录、当前选择、留言及创建时间。当前值为 `independent-chapters-v3`；缺版本的旧 JSON 按 `legacy-v1` 处理。旧档中有调查记录时，账号页进入“版本升级”状态：先下载旧 JSON，用户明确点击开始新版后才覆盖云端；不把旧线索／旧通关直接映射为新剧情。下载文件是人工备份，当前还没有服务器端历史版本列表或 JSON 恢复入口。

单件记录新增 `completedInteractions: string[]`，当前用于保存名单的 `list-mud-cleared`。旧版记录缺该字段时前端按空数组归一化，后端默认空数组；云端只保存“清泥已完成”，不存每一笔擦除轨迹。它不代替 `foundClueIds`，玩家仍须自行登记线索。

保存用 `baseRevision` 防并发覆盖；同一快照重复提交返回既有修订号，不误报冲突。409 真冲突由账号页让玩家选择云端或当前页面。后端离线时把未同步的游戏进度暂存到当前浏览器、标出“本机暂存”，重连时若云端修订号未变则自动补传；若两边都有修改则保留两份并要求玩家选择。云端确认后清除本机暂存，不把未成功上传显示为“云端已保存”。健康接口还返回 `saveContract`，前端拒绝不匹配的旧后端进程。公开部署前仍需数据库备份、HTTPS、Cookie 安全标志、限流与账号恢复。
