# 当前数据与状态契约

以现有代码为准：`frontend/src/types/archive.ts`、`frontend/src/data/objects.ts`、`frontend/src/stores/archive.ts`、`frontend/src/stores/account.ts`、`backend/app.py`。本文件不再定义另一个尚未实现的 `app/src/domain/model.ts`。

## 稳定标识与事件

物件 ID 固定为 `list / map / battery / shoes / bowl`，按此顺序解锁。名单有三处故事线索；其余四章各有四段专属故事线索。数据中每件仍保留三项 `Conclusion` 与两项 `ScreeningDecoy` 用于证据口径，但五章玩家流程均不走通用筛选／盖章。线索 ID 与存档相连，改变它们必须更新 `contentVersion` 并处理旧档。

单件状态：`locked → available → investigating → archived`。只在前一件 `archived` 后开放下一件。名单需拼合／清泥并读完三幕，鼠标与键盘共用完成事件；行军图四条线索从正面发现，点击背注记录核对，随后选择展签；电池盒需掀带、转盒、开盖；草鞋需分开、比尺寸、看补编与鞋底；饭碗需展开包纸、转动与照碗沿、翻底扫光、翻读包纸。五章均保存虚构故事后单独揭露史实，浏览四站才建档。“已浏览”表示材料被打开，理解效果由试玩评估。归档后只读。

`confirmed/inferred/unknown` 表示**故事内证据级别**，不代表某个真实历史人物或文物已被鉴定。历史背景由 `historyRecords.ts` 独立提供，并标识外部来源或待核接入位。真实手迹与游戏名单不可共用同一物件身份。

## 云存档与升级

后端 `Progress` 与前端 `SavedProgress` 包含 `contentVersion`、档案员编号、五件记录、当前选择、留言及创建时间。当前值为 `independent-chapters-v6`；缺版本的旧 JSON 按 `legacy-v1` 处理。v3 电池盒、v4 草鞋、v5 饭碗的旧占位剧情按受影响章节迁移，原记录分别进入 `legacyBatteryRecord`、`legacyShoesRecord`、`legacyBowlRecord`；已归档的老饭碗保留通关资格。更早的有进度旧档仍进入“版本升级”：先下载旧 JSON，用户确认后才开启新版。下载文件是人工备份，目前没有服务器端历史版本列表或 JSON 恢复入口。

`selectedObjectKey` 与 `keeperNote` 配对保存终章票据的物件及留言。首页与档案室的浏览选择保存在页面及路由查询中，浏览其他物件不会改写已生成票据。

单件记录的`completedInteractions: string[]`保存名单的拼合／清泥、行军图背注／展签、电池盒掀带／右侧／开盖和前三章四站史实阅读等稳定事件。旧版记录缺该字段时前端按空数组归一化，后端默认空数组；云端不保存鼠标轨迹、侧光开关或放大倍率。它不代替`foundClueIds`。

保存用 `baseRevision` 防并发覆盖；同一快照重复提交返回既有修订号。GET／PUT `/api/v1/save` 必须携带 `X-Archive-Username`，后端与 Cookie 用户核对，身份不符返回 401。健康接口同时检查 `saveContract: independent-chapters-v6`、`identityContract: account-bound-v1`，前后端及启动脚本须一起更新。

未同步进度用 `unclaimed-pending-save-v2:用户名:页面实例UUID` 分别暂存，避免复制标签页共用写入位置；旧 v1 草稿仍可恢复。恢复先取当前页，再取 v1，再取其他页面最新草稿，复用现有冲突页逐份核对。只有云端确认或玩家明确选择放弃的对应快照且源原文仍匹配时才清除；来源页的新操作继续保留。当前页重连且云端修订未变时自动补传；刷新后的草稿须核对。冲突期间继续本机暂存，暂停上传。401 返回现有登录页并预填原账号；换号时先隔离原账号内存与草稿。旧档无待上传改动时可暂不迁移退出，旧云档保留。公开部署仍需数据库备份、HTTPS、Cookie 安全标志、限流与账号恢复。

连续刷新恢复的草稿沿已保存的来源快照逐层核对清理，来源页的新操作仍保留。本机暂存写入失败后，重连与修订冲突核对保留当前内存中的最新调查，等待玩家选择后再同步。
